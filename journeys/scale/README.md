# Scale and enterprise readiness

Use this path after the production foundation works and growth creates repeated
cost, compliance, platform, regional, or governance decisions.

## Scale in this order

1. [Establish FinOps ownership](https://github.com/Azure-Startup-Field-Guide/guide/tree/main/journeys/scale/finops)
2. [Build compliance readiness from customer requirements](https://github.com/Azure-Startup-Field-Guide/guide/tree/main/journeys/scale/compliance-readiness)
3. [Decide when platform engineering is justified](https://github.com/Azure-Startup-Field-Guide/guide/tree/main/journeys/scale/platform-engineering)
4. [Use recovery targets to decide on multiple regions](https://github.com/Azure-Startup-Field-Guide/guide/tree/main/journeys/scale/multi-region)
5. [Graduate the startup foundation to Azure landing zones](https://github.com/Azure-Startup-Field-Guide/guide/tree/main/journeys/scale/landing-zone-graduation)

## Scale is a change in operating model

Do not add a platform, second region, or enterprise control because the startup
"feels bigger." Add it when a named requirement or repeated failure mode makes
the simpler model insufficient.

Useful evidence includes:

- repeated manual environment setup;
- multiple teams blocked on the same infrastructure path;
- contractual security or data-residency requirements;
- explicit RTO/RPO that one region cannot satisfy;
- material shared-service and policy inconsistency;
- cost allocation that can no longer identify product or tenant economics; and
- subscription or region growth that exceeds the current ownership model.
